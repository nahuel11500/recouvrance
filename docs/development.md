# Development

## Build

The latest stable Rust (`rustup update stable`). On Linux, install the libraries gpui needs:

```sh
sudo apt install pkg-config clang cmake libfontconfig-dev libfreetype-dev libxkbcommon-dev \
  libxkbcommon-x11-dev libwayland-dev libvulkan-dev libx11-xcb-dev libxcb1-dev
```

```sh
cargo run              # debug build
cargo run --release    # what you would use daily
scripts/install.sh     # installs ~/.local/bin/recouvrance and a desktop entry
```

## Checks (what CI runs)

```sh
cargo fmt --all --check
cargo clippy --all-targets -- -D warnings
cargo clippy --all-targets --features dev -- -D warnings
cargo test --features dev
cargo deny check        # licenses, advisories, sources (cargo install cargo-deny)
typos                   # spelling (cargo install typos-cli)
```

## Developer tools (`--features dev`)

The `dev` feature adds tools that are not part of the app. The `RECOUVRANCE_*` variables below are
read only in `dev` builds; a release build ignores them.

**Snapshots**: render the real UI off-screen to a PNG, against a real cluster:

```sh
RECOUVRANCE_CONTEXT=kind-dev RECOUVRANCE_KIND=pods RECOUVRANCE_NS=default RECOUVRANCE_SELECT=0 \
RECOUVRANCE_TAB=logs cargo run --features dev -- --snapshot out.png 8
```

Useful variables: `RECOUVRANCE_PAGE` (`apply`, `settings`, `cluster`, `access`…),
`RECOUVRANCE_FILTER`, `RECOUVRANCE_ACT` (comma-separated hooks, see `src/app/demo.rs` and
`src/details/demo.rs`), `RECOUVRANCE_INPUT` (`click:x,y;key:enter;wait:2`), `RECOUVRANCE_WRITES=1`,
`RECOUVRANCE_DARK=1`, `RECOUVRANCE_ZOOM`. Point `XDG_CONFIG_HOME` at a scratch folder to keep your
settings untouched.

**Smoke checks**: `RECOUVRANCE_SMOKE=<context> cargo run --features dev` lists types and watches
pods; add `RECOUVRANCE_LISTTIME=1`, `RECOUVRANCE_PROBLEMS=1`, or dry runs such as
`RECOUVRANCE_NODESHELLDRY=<node>` (see `src/dev/smoke.rs`).

**README screenshots** live on the `media` branch, so `main` stays small. Take them on a throwaway
kind cluster with demo workloads, never a real one (names of clusters, namespaces and objects show).
Use a scratch `XDG_CONFIG_HOME` and `XDG_DATA_HOME` too, so your settings and agent activity stay out
of the picture.

## Fuzzing

`fuzz/` holds [cargo-fuzz](https://github.com/rust-fuzz/cargo-fuzz) targets for the code that reads
untrusted text: the table filter (`filter`), Kubernetes quantities (`quantity`) and YAML (`yaml`,
which also checks that what the YAML view writes reads back as the same value). They build the
app's own `src/filter_syntax.rs`, `src/quantity.rs`, `src/glob.rs` and `src/yaml.rs` through
`#[path]`, so those files may only use std, regex and serde. ClusterFuzzLite runs them
(`.clusterfuzzlite/`, `.github/workflows/fuzz.yml`): 5 minutes after each push to `main` that
touches the code, 30 every week. Locally, with a nightly toolchain:

```sh
cargo install cargo-fuzz
cargo +nightly fuzz run filter -- -max_total_time=60
```

## Testing writes

Use a throwaway cluster, never a shared one:

```sh
kind create cluster --name recouvrance-dev
RECOUVRANCE_CONTEXT=kind-recouvrance-dev cargo run --features dev
```

## Code conventions

- `cargo fmt` (see `rustfmt.toml`) and clippy clean.
- Modules by concern; files under ~800 lines. UI in `app/`, `details/`, `overview/`, `ui/`; API
  calls in `k8s/`; logic that can be unit-tested in plain modules (`diagnose`, `rbac`, `schema`…).
- Comments explain *why*; doc comments on public items say what they return.
- Writes always go through a confirmation that shows the `kubectl` equivalent, and a dry run when
  the API allows it.

## Maintainers

`main` is protected by the ruleset in `.github/rulesets/main.json` (pull requests with squash
merges, linear and signed history, the `CI result` check) and release tags by
`.github/rulesets/tags.json` (only repository admins create, move or delete `v*` tags).
`scripts/protect-main.sh` creates or updates both by name, so run it again after changing them
(rulesets need a public repository or a paid GitHub plan).

### Releases

The flow is in [CONTRIBUTING](../CONTRIBUTING.md#releases): merge the *Release vX.Y.Z* pull request
that release-plz keeps open. Behind it:

- **Workflows.** `release-plz.yml` (on pushes to `main`) opens the release pull request and, once it
  is merged, pushes the tag through the GitHub API and drafts the GitHub
  release. The tag starts `release.yml` (generated by dist), which builds the archives, the install
  script and the updater, calls `linux-packages.yml` for the `.deb` and AppImage, then uploads
  everything and publishes the release. release-plz does nothing until the repository variable
  `RELEASES_ENABLED` is `true`, and without its tags `release.yml` never starts.
- **The `release` environment** holds the release secrets. Both release-plz jobs run in it, and its
  deployment branch rule (`main` only) keeps every other branch and workflow away from them. Keep
  release secrets out of the repository-level secrets: `release.yml` calls `linux-packages.yml`
  with `secrets: inherit` (dist writes that line), which passes repository secrets, not environment
  ones.
  - `RELEASE_PLZ_TOKEN`: a fine-grained token of a repository admin (the tag ruleset lets admins
    through), for this repository only, with contents and pull requests: write. A personal token
    rather than `GITHUB_TOKEN`, because events made with `GITHUB_TOKEN` start no workflow: the tag
    must start `release.yml` and the release pull request must get CI.
  - `CARGO_REGISTRY_TOKEN`: only for a first crates.io publish (below); not set today.
- **GitHub only.** `release-plz.toml` sets `publish = false` and `git_only = true` for the crate:
  releases go to GitHub only, nothing is published to crates.io, and versions come from the `v*`
  tags. A release on GitHub can be deleted (release and tag) if something is wrong; a crates.io
  version never can.
- **Publishing to crates.io, if decided: token first, then trusted publishing.** Trusted publishing
  (OIDC, no stored token) only works for a crate that already exists, so:
  1. Create a crates.io token scoped to `recouvrance` with **publish-new** and publish-update,
     store it as `CARGO_REGISTRY_TOKEN` in the `release` environment (or run `cargo publish` by
     hand once), then remove the `[[package]]` section of `release-plz.toml` in the release pull
     request. Without the token the publish job fails, and with it the tag and the binaries.
  2. Once the crate is on crates.io, add a trusted publisher in its settings: owner `nahuel11500`,
     repository `recouvrance`, workflow `release-plz.yml`, environment `release`.
  3. Delete the `CARGO_REGISTRY_TOKEN` secret and revoke the token on crates.io. Without it, the
     publish job gets a short-lived token through `id-token: write`.
- **dist.** After changing `dist-workspace.toml`, run `dist generate` and commit
  `.github/workflows/release.yml` (`dist generate --check` tells whether it is current; the release
  workflow's plan step fails while it is out of date). `release.yml` is
  never edited by hand (`allow-dirty` stays unset): what it must do is set through dist's config,
  such as `github-custom-job-permissions` for the packages job. Dependabot skips it
  (`exclude-paths` in `.github/dependabot.yml`); its actions move when dist is upgraded
  (`dist selfupdate`, then `dist generate`).
- **Pinned tools.** Workflows that hold write tokens or secrets (`release-plz.yml`,
  `linux-packages.yml`, `pr-title.yml`) pin actions by commit SHA, with the version in a comment;
  Dependabot updates both. `linux-packages.yml` also checks appimagetool and the AppImage runtime
  against pinned sha256 sums: to update them, download the new assets, compute their sha256 and
  replace the URL and sum together.
- **Attestations.** dist attests the archives (`github-attestations`) and `linux-packages.yml`
  attests the `.deb` and AppImage. Check any of them with
  `gh attestation verify <file> --repo nahuel11500/recouvrance`.

### Launch checklist

Before the first release of the public repository:

1. Make the repository public; add the topics `kubernetes`, `mcp`, `rust`, `gpui`, `desktop`.
2. Run `scripts/protect-main.sh` (both rulesets).
3. Settings → Code security: enable secret scanning, push protection and private vulnerability
   reporting (SECURITY.md and the code of conduct send reports there).
4. Settings → Actions → General: require approval for workflows from fork pull requests of all
   outside collaborators.
5. Settings → Environments: create `release`, deployment branches limited to `main`, with the
   secret `RELEASE_PLZ_TOKEN`.
6. Set the repository variable `RELEASES_ENABLED` to `true`. The next push to `main` tags `v0.0.1`
   (no tag exists yet), opens its GitHub release and starts the release build: a test release,
   GitHub only.

Releases stay GitHub only until the crate is published to crates.io (above).
